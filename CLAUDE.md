# CalClassCoordinator

Berkeley class tools: a seat alert watcher plus a planner (majors/requirements, transcript import, ML enrollment-timing predictions by professor). Each top-level folder is one component, usually built in its own thread/branch. Keep this file short; add a few lines for your component, don't rewrite others'.

## Layout

| Folder | What | Notes |
|---|---|---|
| `watcher/` | Seat alert watcher (Python 3.11+). Polls classes.berkeley.edu (fallback Berkeleytime), parses open, reserved and waitlist seats, diffs, alerts. | `python -m watcher --help`. Writes `data/seats/latest.json`. Optional HTTP API: `python -m watcher serve` (GET /seats, POST /subscriptions). |
| `data/` | Historical enrollment data + by-professor ML model. `data/seats/` is owned by the watcher. | Built by the data/ML thread. |
| `data/requirements/`, `data/courses.json` | Every major, minor and college (L&S, CDSS, CoE, …) with requirements, breadth, and which classes fulfill them; plus the course list with breadth/AC/R&C tags. Generated, do not hand-edit. | Built by the requirements thread. See "Requirements data" below and `docs/requirements-data.md`. |
| `insights/`, `data/insights/` | Class insights: grades, student ratings, written reviews, midterms by professor, RateMyProfessors, Reddit; a difficulty and a "should I take it" rating per class and per professor. | `python -m insights --help`. See "Class insights" below. |
| `data/schedule/` | Lecture, discussion and lab times per term for the weekly schedule builder. Generated, do not hand-edit. | `python -m watcher import-schedule`. See "Class times and schedule builder" below. |
| `web/` | Planner web app (accounts, transcript import, schedule, req checkoff, seat badges). | Built by the planner thread. |
| `docs/` | Cross-component contracts, e.g. `docs/data-contracts.md`, `docs/berkeleytime-api.md`. | |
| `tests/` | pytest for Python components; fixtures in `tests/fixtures/`. | `python -m pytest` |

## Conventions

- Data contracts between components are JSON files in the repo; change them additively only and document in `docs/data-contracts.md`.
- Seat snapshot contract (`data/seats/latest.json`, also GET /seats): `{updatedAt, term, sections:[{course, classNumber, section, term, instructor, enrolled, capacity, waitlisted, waitlistCapacity, open, reserved:[{group, enrolled, capacity}], status, url, source, fetchedAt}]}`.
- Scrape politely: identify as "CalClassCoordinator", time out requests, never poll faster than every 30s, cache where possible.
- Scrapers keep pure parse functions separate from network code and are tested offline against saved pages in `tests/fixtures/`.
- Secrets (SMTP passwords, webhook URLs, API keys) come from env vars named in config, never committed. `watcher.yaml` and `.env` are gitignored.
- `OWNER_NOTES.md` is the owner's personal design log (what data, how scraped, how tested, why X over Y), one section per component. It is not in the repo (gitignored, so it stays private if the repo is public): the copy is `/mnt/project-files/notes/OWNER_NOTES.md` in the project's shared files. Update your section there when your design changes, and never commit it. `README.md` is public user docs.
- Discord: `watcher/discord_server.py` builds the public server (`discord-server`), `watcher/discord_bot.py` is the opt-in bot (`discord-bot`), texts in `watcher/discord_content.py`. All server state is in the gitignored `discord_channels.json`; test against the fake in `tests/test_discord_server.py` (cloud sessions cannot reach discord.com).
- Cloud sessions: classes.berkeley.edu and berkeleytime.com are allowed in the network policy; other hosts may need adding.

## Requirements data (`data/requirements/`, `data/courses.json`, `scripts/`)

- Everything under `data/requirements/` (except `overrides/`), `data/courses.json`, `data/course_details.json` and `data/subjects.json` is generated by `python3 scripts/build_requirements.py` from the committed snapshot in `data/raw/catalog/`. Do not edit those files by hand; change the converter or add an override, then rebuild.
- Source is the official catalog, undergraduate.catalog.berkeley.edu (Coursedog), catalog year 2026-27. To refresh: `node scripts/scrape_catalog.js programs-list && node scripts/scrape_catalog.js programs && node scripts/scrape_catalog.js courses-list && python3 scripts/fetch_payloads.py programs && python3 scripts/fetch_payloads.py courses && python3 scripts/build_requirements.py --pack`. Needs Playwright and network access to undergraduate.catalog.berkeley.edu, app.coursedog.com and static.catalog.prod.coursedog.com. The course download is throttled by the site and takes about an hour.
- Course ids are `"SUBJECT NUMBER"` with the catalog's subject code, which has no spaces or punctuation: `COMPSCI 61A`, `ELENG 16A`, `LS C70T`, `PBHLTH 142`. `data/subjects.json` maps older spellings (`EL ENG`, `L & S`, `CS`) to codes.
- Files: `colleges.json`, `majors.json` (each major has `requirementGroupIds`, `collegeGroupId`, `universityGroupId`), `minors.json`, `groups/<id>.json`. A student's full checklist is the major group + the major's `collegeGroupId` group + `university`. Use the major's `collegeGroupId`, not the college default, because a few programs (M.E.T., Chemical Engineering, Environmental Economics & Policy) have their own college rules.
- Rule types: `course`, `allOf`, `anyOf`, `nOf{n}`, `filter{count|minUnits, filter:{courses,subjects,minNumber,maxNumber,breadth,attribute,exclude}}`, `units{minUnits, filter}`, `manual{text}`. Filter keys combine with AND. `manual` means the catalog only states the rule in prose; show it as a self-check box. A manual rule may carry `mentionedCourses` (course ids found in that prose) as a hint.
- Attributes on courses: `AC`, `AH&I`, `ELW`, `RCA`, `RCB`, `FL` (second-semester language or higher), `UD` (numbered 100-199), `HSS` (derived: has a humanities/social-science breadth area, or is R&C or AC). Breadth names: Arts & Literature, Biological Science, Historical Studies, International Studies, Philosophy & Values, Physical Science, Social & Behavioral Sciences.
- Hand corrections go in `data/requirements/overrides/<groupId>.json` (`{"why", "source", "replace": {"<requirementId>": {"rule": ...}}}`) and are applied on every build. College and university rules that the catalog gives only as prose are written in `Builder.named_set` in the build script.
- Additive fields: group `choices: [{id, title, pick, options: [{id, title}]}]` and requirement `choice` + `option` (concentrations, emphases, tracks: a student completes `pick` options; requirements without them are for everyone); sub-rule `label` inside merged alternatives; `allOf` `overlap: true` (sub-rules may reuse the same class); course `source: "berkeleytime"`; major/minor `aliases`.
- More additive fields: course `sameAs` (same class under another number: `MATH 1A` <-> `MATH 51`; symmetric, closed, never overlaps `crossListed`; curated extras in `SAME_AS` in the build script), `retired: true` (old-number stub), `popularity` (int, enrollment total, for search order); requirement `optional: true`; group `programType` (`major` | `joint-major` | `dual-degree`). Option sections read `"<Option>: <Section>"`. The 120-unit minimum lives only in `university`; college/university rows assume independent evaluation.
- Which programs have a choice is decided by hand in `data/requirements/overrides/choices.json` (format in its `_about`). Per-group override files also take `renameSections`, `renameRules` and `merge` (alternatives listed as separate rows). Anything in an override that matches nothing fails the build.
- Course completeness: `data/raw/catalog/course_index.json.gz` is the catalog's own CSV export of course ids; `--pack` and `--strict` fail if a listed course, or an undergraduate course used by `data/predictions/predictions.json`, is missing. To repair: `node scripts/scrape_catalog.js courses-list && python3 scripts/fetch_payloads.py courses --missing && python3 scripts/build_requirements.py --pack --strict` (pack merges into the existing snapshot). Courses the catalog no longer lists come from `python3 scripts/fetch_supplement.py` -> `data/raw/supplement/courses.json`.
- `data/requirements/REPORT.md` is regenerated on each build: counts, warnings, and which groups still rely on self-check rules. Tests: `python -m pytest tests/test_requirements_data.py`.

## Enrollment scrapers (`ml/scrapers/`)

- `classes_berkeley.py`: classes.berkeley.edu listing (`/search/class?f[0]=term:<id>&page=N`, 18/page) -> class pages (`/content/<yyyy>-<season>-<subj>-<num>-<sec>-<comp>-<sec>`); counts come from the drupal-settings JSON `ucb.enrollment`. Output `data/enrollment/classes/sections.csv` (+ `sections_extra.csv`, `term_phases.json`). Raw HTML cached gzip'd in `/tmp/claude-0/cbcache/raw`; re-run is resumable: `python3 ml/scrapers/classes_berkeley.py --stage all --workers 12 --rate 4`. Class pages are slow (~5-8 s server render), so the full run takes many hours.
- The site returns 403 to browser-like User-Agents; the "CalClassCoordinator" UA works. Uses curl subprocesses because requests through the sandbox proxy sometimes hung.
- `berkeleytime.py`: Berkeleytime GraphQL (`POST /api/graphql`, persisted ops only: body `{"id": sha256(minified query), "variables"}`). `GetCatalogClassIdentities` lists a term's classes, `GetClass` gives primary-section run-length daily history (endTime inclusive) + instructors + sections. Output `data/enrollment/berkeleytime/{timeseries.csv.gz,sections.csv,timeframes.json}`; cache `/tmp/claude-0/bt/cache` (resumable): `python3 ml/scrapers/berkeleytime.py all --level undergrad`. If the API answers "Invalid persisted operation request", run `refresh-ops` (needs graphql-core).

## Enrollment predictor (`ml/predictor/`)

- `pip install -e ".[ml,dev]"`. `python -m ml.predictor build --term "Spring 2027"` rebuilds `data/enrollment/observations.csv`, backtests, trains, and writes `data/predictions/predictions.json` (about 4 min). `python -m ml.predictor predict "COMPSCI 61A" "John DeNero"` for one class (needs a prior `build`; the `.joblib` model is gitignored).
- Contract for the planner: `docs/predictions.md`. Keyed by course + professor; `professorSeenBefore`, `warning`, `basis` say what history the estimate rests on. Add fields only.
- Never train on the term being predicted; features for a term use strictly earlier terms (`rolling_features`). Labels: "full" = enrolled >= 97% of capacity or waitlist > 0, counted from Phase 1 start (earlier snapshots are stale pre-rollover data).
- Expansion and waitlists: observations carry `capacity_start`, `expansion_ratio`, `waitlist_peak`, `waitlist_cleared`; the capacity feature is the Phase 1 starting capacity, never the final one. `waitRisk` (full when you arrive x waitlist does not clear) drives `recommendation` and the planner's Phase 1 picks under the unit cap (`web/src/lib/enrollPlan.ts`, default 13.5).
- Input schemas: `data/enrollment/SCHEMA.md`. Phase names the model uses are exactly `Phase 1`, `Phase 2`, `Adjustment Period`; other entries in `phases.json` are ignored except `Add/Drop Deadline`, which caps the adjustment period.

## Class times and schedule builder (`watcher/schedule.py`, `watcher/lookup.py`, `data/schedule/`)

- Contract: `docs/schedule.md`. A course in a term is a list of classes `{number, primary: SECTION, sections: [SECTION]}`; meetings are `{days: [0=Mon..6], start: "13:00", end, location}`.
- `data/schedule/<yyyy>-<season>.json` + `index.json` are generated by `python -m watcher import-schedule --term "2027 Spring" [--cache DIR]` (Berkeleytime, about an hour per term, resumable). Do not hand-edit. `.github/workflows/refresh-schedule.yml` re-imports twice a month and opens a PR.
- Live lookups: watcher API `GET /lookup?course=&term=` (`LookupService`: 5 min cache per course, shared in-flight fetch, 6 h cool-off after 403/429). Only `web/src/lib/server/scheduleData.ts` calls it, behind `GET /api/sections`.
- classes.berkeley.edu returns 403 to Fly, so `deploy/watcher.prod.yaml` sets `lookup_sources: [berkeleytime]`. Never disguise requests to get around the block.
- Berkeleytime lists sections and classes the official schedule hides; keep `drop_placeholder_sections` and the `anyPrintInScheduleOfClasses` filter.
- A term with no file falls back to the latest earlier same-season term, marked `tentative` (no seat counts). The student's picks are `PlannedCourse.sections` (class numbers).

## Production (`Dockerfile`, `deploy/`, `fly.toml`, `.github/workflows/`)

- One image runs both processes via `deploy/start.sh`: `node server.js` (Next standalone, port 3000) and `python -m watcher prod` (poll loop + API on 127.0.0.1:8765 + Discord bot when `DISCORD_BOT_TOKEN` is set). State is on the `/data` volume: `/data/web/planner.db`, `/data/watcher/*`. Setup steps: `docs/deploy.md`.
- Env names are shared by both sides: `APP_URL`, `SMTP_HOST/PORT/USER/PASSWORD`, `MAIL_FROM`, `WATCHER_API_TOKEN`, `PLAN_ENCRYPTION_KEY`, `DISCORD_BOT_TOKEN`. Full list in `deploy/.env.example`; production watcher config is the secret-free `deploy/watcher.prod.yaml`.
- The watcher API requires `Authorization: Bearer $WATCHER_API_TOKEN` when the token is set and refuses a non-loopback bind without one. Only `web/src/lib/server/watcher.ts` calls it.
- Every mutating web API route must call `checkOrigin` and a rate limit (`web/src/lib/server/{origin,rateLimit}.ts`); a test fails if one does not. Seat alerts need a signed-in, verified account and always use the account's email.
- Terms are `"2027 Spring"` in the planner and watcher; the predictor writes `"Spring 2027"`, normalized in `web/src/lib/catalog.ts`.
- CI (`ci.yml`): pytest with `.[dev,discord,ml]`, requirements data in sync, web lint/typecheck/test/build, Docker build + health check. `deploy.yml` deploys `main` to Fly after CI when `FLY_API_TOKEN` exists.

## Class insights (`insights/`, `data/insights/`)

- Pipeline: `python -m insights collect-berkeleytime` (about 2 hours, resumable), `collect-rmp --reviews 400`, `collect-reddit --top 300` fill the gitignored cache `data/raw/insights/`; `pack` writes the committed snapshots in `data/insights/raw/`; `build` reads only those snapshots and writes `insights.json`, `details/<SUBJECT>.json` and `REPORT.md`. Do not hand-edit the generated files.
- `build` is deterministic and offline. After changing weights or code in `insights/build.py`, rerun it and commit the output; `tests/test_insights.py` fails when `data/insights/` is stale.
- RateMyProfessors and Reddit are not reachable from cloud sessions (network policy; Reddit also blocks cloud IPs). Run those two collectors on the owner's computer, or add `www.ratemyprofessors.com` to the allowlist and set `REDDIT_CLIENT_ID` / `REDDIT_CLIENT_SECRET`.
- Berkeleytime only accepts persisted queries; the texts are in `insights/bt_queries.json`. On HTTP 400, run `python -m insights refresh-queries`.
- `data/insights/summaries.json` (optional, `{course: {summary, sentimentScore 1..5, evidence}}`) holds model-written summaries of written reviews; the build uses them for the `sentiment` text and as one small signal.
- Rating weights are constants at the top of `insights/build.py`; the method is explained in `data/insights/REPORT.md` and `OWNER_NOTES.md`.
